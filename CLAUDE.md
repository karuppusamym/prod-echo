# Prod Echo

Prod Echo rebuilds the screens UiPath bots use, over a copy of the data they use, so agentic
automations can be tested without touching production and without waiting for app teams to stand
up environments. Read `docs/01-problem-statement.md` once; everything else here assumes it.

## How work happens in this repo

- Work is **one plan item at a time**, in order, from `docs/03-plan.md`. Do not start the next item
  until the current item's Definition of Done is met and its checkbox is ticked in the plan.
- Each item ends with: code, tests, a one-paragraph entry in `docs/CHANGELOG.md`, and the plan
  checkbox ticked. If an item cannot be finished as written, stop and say why; do not widen it.
- Every item must be demonstrable against the **local harness** (`harness/`) before it is run against
  anything real. "It would work in prod" is not done.
- When a format or behavior is unknown (a UiPath log field, a NetLog event type, an Oracle quirk),
  ask for a sample file. Do not invent a format and code to it.
- Prefer boring choices. One module, one CLI subcommand, SQLite for the harness, plain files on disk.
  Push back in the PR description if an item seems to need a queue, a scheduler or a framework.

## Hard constraints

- **No production credentials, hostnames, or data in this repo**, ever, including in tests, fixtures,
  notebooks or docs. Fixtures are generated by `harness/` or are hand-written synthetic examples.
- **Nothing here writes to a production system.** Readers only. The only writes are to the Echo DB
  and the generated apps, both of which this repo owns.
- Self-hosted only: no cloud-managed services, no SaaS calls from code.
- Deterministic data handling: no LLM-generated records anywhere in the data path. LLM use is fine
  for developer tooling and is otherwise out of scope.
- Masking is deterministic and keyed (HMAC / FF1). One key per environment, read from an environment
  variable, never from a file in this repo. Same input, same output, every run.
- Captures record real customer data when run in production. Capture *parsers* in this repo are
  tested only on harness output.

## Tech stack (decided; see docs/adr)

- Python 3.11+, `uv` for environments, `ruff` for lint/format, `pytest` for tests, `pydantic` v2 for
  every contract in `docs/04`, `typer` for the CLI (`echo <area> <verb>`), `SQLAlchemy` for DB access
  (SQLite in the harness; Oracle / SQL Server / DB2 dialects behind the same interface).
- Browser work uses Playwright. The CDP recorder attaches to an **existing** Chrome/Edge over the
  DevTools protocol; it never launches its own browser outside the harness.
- Generated apps are static templates rendered by a small FastAPI data service over the Echo DB,
  plus one generic behavior script (ADR-008, ADR-010).
- No Airflow, Temporal, Kafka, Docker-compose sprawl, or ORM-heavy layers until an item's DoD
  cannot be met without one, and then only with an ADR.

## Commands

```
uv sync                       install
uv run echo --help            CLI
uv run pytest                 tests (fast; no network, no browsers unless marked)
uv run pytest -m browser      tests that drive the harness in a real Chromium
uv run echo harness up        start both fake apps on localhost
uv run echo harness bot       run the fake bot once; writes a Verbose-shaped log and a capture bundle
uv run echo pipeline harness  the whole chain on the harness (needs ECHO_MASK_KEY, 16+ bytes)
uv run echo capture probe     optional UAT probing on the harness (I-22b)
uv run echo --db <alias> --process <name> --xaml <dir> data bind   global options pick what steps run on
uv run ruff check . && uv run ruff format --check .
```

## Coding conventions

- Every contract is a pydantic model in `echo/<area>/models.py` with an example file in `specs/`.
  Tests load the example and assert it validates. Changing a contract means changing the example.
- CLI subcommands are thin: parse args, call one function, print or write. Logic lives in modules.
- Functions that read capture files take a path and return models; they never print.
- Timestamps are UTC ISO-8601 strings. Run ids are `run_<YYYYMMDDTHHMMSSZ>_<6 hex>`.
- Log with the standard library `logging`; never `print` from library code.
- Type hints everywhere; `ruff` with the default rules plus `I` (isort) and `B` (bugbear).
- Tests name the behavior: `test_netlog_parser_lists_every_url_the_bot_requested`.

## Slash commands available in Claude Code

- `/next-item` — read `docs/03-plan.md`, find the first unchecked item, restate its DoD, and start it.
- `/finish-item` — run tests and lint, write the CHANGELOG paragraph, tick the checkbox, summarize.
- `/review-item <id>` — review a finished item against its DoD and the hard constraints above.

## Things to ask the human about before acting

- Any real sample file (XAML, robot log export, NetLog, DDL) — never fabricate one.
- The masking field list for an app — the data owner decides, not the code.
- Anything that would run on a robot host, a replica, or a prod-adjacent network.
- Adding a dependency outside the stack above.
